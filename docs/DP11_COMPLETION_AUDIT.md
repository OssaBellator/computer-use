## Source status

The originally supplied `DP11 preparation and expansion^.docx` physically truncates during DKG-84, so the repository's earlier audit could only prove DKG-79 through DKG-83 from that file. A later fuller DP11 expansion reviewed during implementation provides high-level DKG-84 embodiment-routing, DKG-85 evaluation, DKG-86 progressive-enablement, and stronger production-gate criteria. This audit therefore no longer treats DKG-85/DKG-86 as undefined; it separates mechanism coverage, empirical evidence, and remaining production proof.

Case ordering does not affect the digest, while any replay-content change does. - Balanced replay sampling can deterministically cap overrepresented partition/application/provider domains before diagnostic evaluation. The cap is only a sampling budget: the selector reports dropped cases and hard-codes `thresholdApplied:false`, `promotionEligible:false`, and `authorityGranted:false`. Observation validity remains enforced downstream by the strict replay corpus/evaluator rather than being weakened in the sampler.
- The semantic recipe review registry stores immutable manifests by exact digest, validates parent lineage before accepting child revisions, supports parallel candidate branches, and resolves recipes only by explicit recipe ID plus digest. It intentionally exposes no `latest`, `active`, `promote`, or dispatch shortcut, so registering a newer learned/corrected candidate cannot silently make it executable.
- Release-environment proof is now an explicit production-gate input rather than an inference from generic host/VM source breadth. Policy must name every required release environment; source records define where executions actually occurred, and explicit evidence bindings must cover every attempted case observed in that environment. Each required environment is independently re-evaluated against the same approved stratum attempted/trial/success/failure/UNKNOWN/embodiment/source/application/provider thresholds, global application/provider and required-source-kind breadth, every hard safety claim at its configured passing-case minimum, at least one passing exact-level rollout plus disablement case, and provenance-bound zero-tolerance incident evidence from that same environment. Zero-tolerance totals must equal the aggregate of bounded evidence records anchored to an actual empirical case/source whose exact Git SHA and environment identity match the record; detached or caller-invented evidence IDs cannot satisfy the gate, and naked caller-supplied zero counts cannot satisfy validation. Global claim, DKG86, or incident evidence from another environment cannot substitute for release-environment proof. Caller-side relabeling cannot turn a host/VM run into release-environment proof, and failed/UNKNOWN environment cases cannot be hidden by omitting their binding. The gate exposes measured per-environment coverage. No DP11 release-environment identity is approved yet, so the current corpus intentionally supplies no such binding and remains blocked.
- DKG86 rollout proof is now separate from capability eligibility: the production proof for the selected `CU-*` level must name passing empirical rollout cases whose ledger entries explicitly declare that same CU level, and disablement evidence is independently required with the same exact-level binding. The entire enablement configuration (validated granular capability profile, complete CU policy table, target level, rollout IDs, and disablement IDs) is canonicalized and SHA-256-bound to immutable review provenance; missing or stale approval blocks release. Runtime capability profiles reject unknown capability names and invalid support states rather than trusting TypeScript-only shapes. Empty rollout evidence, missing/non-passing cases, missing level identity, or level mismatch fail closed for rollout or disablement. This mechanism does not choose or approve a production CU level or capability mapping.
- Quantitative production policy approval is now provenance-bound rather than implied by a syntactically valid policy object. The gate computes a canonical SHA-256 digest over normalized threshold/source/application/provider/release-environment policy contents and requires an explicit approval record binding that exact digest and policy ID to a bounded review evidence ID and exact Git SHA. Missing approval blocks eligibility; policy-ID/digest mismatch blocks eligibility; malformed review provenance fails validation. No DP11 quantitative policy approval record is supplied by the repository, so this mechanism does not manufacture the still-missing production approval.

## Stronger production gate still open

DP11 must not be promoted merely because all mechanisms exist. The production gate still needs a release-facing quantitative corpus that demonstrates, at minimum:

- no blind retry after possible consequential dispatch;
- no consequential success asserted solely from dispatch;
- authoritative state-transition verification where semantic verification exists;
- prompt-injection/hostile-content authority isolation;
- human-interference handling and UNKNOWN semantics;
- routing quality and fallback visibility across multiple embodiments/providers;
- recovery/fault-injection behavior, including stale identity and process-loss cases;
- privacy/secret-retention behavior for credential-adjacent workflows;
- cross-embodiment equivalence without authority flattening;
- long-horizon suspend/resume, re-authentication, anti-rollback, and hierarchical-task behavior;
- explicit disablement/progressive-enablement policy with no automatic authority inheritance.

## Release decision

`main` promotion remains blocked, but no longer because DKG-84 through DKG-86 are undefined. It is blocked because the implementation has reached **mechanism-complete / baseline-evidence-present** status without yet reaching **production-proof-complete** status.

Promotion should require an explicit production-gate policy with quantitative thresholds, a DKG85 corpus satisfying that policy in the release environment, and a reviewed DKG86 CU-level rollout/disablement mapping. Until those conditions are met, `dp11-leading-edge-foundations` remains the integration branch and `main` stays unchanged.
